## Pre-Execution Checks

**Global executor registry (MANDATORY - before anything else)**:

- Read `~/.specify/models.json`. Do not read a project-local models file.
- Require valid JSON with `version: 2` and non-empty `models` and `clis`
  arrays.
- If the file is missing or invalid, STOP and tell the user to run
  `__SPECKIT_COMMAND_MODELS__`.
- This command runs in the principal CLI. It coordinates task workers but is
  never delegated as a whole and has no entry in the `commands` array.

**Check for extension hooks (before implementation)**:
- Check if `.specify/extensions.yml` exists in the project root.
- If it exists, read it and look for entries under the `hooks.before_implement` key
- If the YAML cannot be parsed or is invalid, skip hook checking silently and continue normally
- Filter out hooks where `enabled` is explicitly `false`. Treat hooks without an `enabled` field as enabled by default.
- For each remaining hook, do **not** attempt to interpret or evaluate hook `condition` expressions:
  - If the hook has no `condition` field, or it is null/empty, treat the hook as executable
  - If the hook defines a non-empty `condition`, skip the hook and leave condition evaluation to the HookExecutor implementation
- For each executable hook, output the following based on its `optional` flag:
  - **Optional hook** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **Mandatory hook** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    After emitting the block above you MUST actually invoke the hook and wait for it to finish before continuing. Run it the same way you would run the command yourself in this agent/session (the invocation may differ from the literal `{command}` id shown above, e.g. a skills-mode agent runs it as `/skill:speckit-...` or `$speckit-...`). Emitting the block alone does not run the hook.
- If no hooks are registered or `.specify/extensions.yml` does not exist, skip silently

5. Parse tasks.md structure and extract:
   - **Task phases**: Setup, Tests, Core, Integration, Polish
   - **Task dependencies**: Sequential vs parallel execution rules
   - **Task details**: ID, description, file paths, parallel markers [P]
   - **Executor labels**:
     `[E:cli=<cli>|model=<model>|effort=<effort>|context=<tokens>]`
     assignments generated by the `tasks` command
   - **Execution flow**: Order and dependency requirements

6. Execute implementation following the task plan:
   - **No classification or selection**: `implement` MUST NOT classify a task,
     select another model, or modify its assignment. The `tasks` command
     already made that decision.
   - **Require a complete assignment**: If any pending task lacks a valid
     `[E:...]` label, STOP and tell the user to rerun `__SPECKIT_COMMAND_TASKS__`.
     Never apply a default executor.
   - **Resolve the assigned route**:
     - Find the label's canonical `model` in the global `models` array.
     - Find the label's `cli` in the global `clis` array.
     - Find the model availability matching that CLI and obtain the exact
       CLI-specific model ID.
     - Validate the assigned effort against `effort_levels`.
     - Validate that assigned context is positive and does not exceed the
       availability's effective `context_window`.
     - Load the selected CLI's structured execution recipe.
   - **Build the worker invocation**:
     - Substitute the exact CLI model ID, assigned effort, assigned context,
       and project root into the recipe.
     - Keep argv as an argument array and never evaluate a shell string.
     - Send a focused worker prompt containing the task text, required project
       context, dependencies, relevant files, acceptance criteria, and
       validation commands.
     - Deliver the prompt using the recipe's `stdin`, `argument`, or `file`
       transport and launch the assigned CLI from the project root.
     - Wait for completion and capture output, changed files, tests, and exit
       status.
   - **Assigned executor failures**: If the assigned CLI/model cannot be
     launched or fails, report the exact task and assignment. Do not silently
     choose another CLI or model; assignment changes belong to `tasks` or an
     explicit user decision.
   - **Phase-by-phase execution**: Complete each phase before moving to the next
   - **Respect dependencies**: Run sequential tasks in order; tasks marked [P] can run together
   - **Parallel execution (MANDATORY when supported)**: The principal CLI must
     parallelize ready [P] tasks by launching each task's assigned CLI:
     - Within the current phase, group ready [P] tasks (dependencies met) into a batch. Exclude from the same batch any two tasks that touch the same file.
     - Launch the whole batch concurrently when the assigned CLI recipes
       support independent processes. Each worker receives only the context it
       needs and uses exactly its recorded assignment.
     - Wait for the entire batch to finish before dispatching tasks that depend on it. Then form the next batch.
     - Sequential tasks (no [P]) always run one at a time in order.
     - If the environment has no concurrency support, run [P] tasks
       sequentially and note it in the completion report.
   - **Follow TDD approach**: Execute test tasks before their corresponding implementation tasks
   - **File-based coordination**: Tasks affecting the same files must run sequentially — never in the same parallel batch
   - **Validation checkpoints**: Verify each phase completion before proceeding

7. Implementation execution rules:
   - **Setup first**: Initialize project structure, dependencies, configuration
   - **Tests before code**: If you need to write tests for contracts, entities, and integration scenarios
   - **Core development**: Implement models, services, CLI commands, endpoints
   - **Integration work**: Database connections, middleware, logging, external services
   - **Polish and validation**: Unit tests, performance optimization, documentation

8. Progress tracking and error handling:
   - Report progress after each completed task
   - Halt execution if any non-parallel task fails
   - For parallel tasks [P], continue with successful tasks, report failed ones
   - Provide clear error messages with context for debugging
   - Suggest next steps if implementation cannot proceed
   - **IMPORTANT** For completed tasks, make sure to mark the task off as [X] in the tasks file.

9. Completion validation:
   - Verify all required tasks are completed
   - Check that implemented features match the original specification
   - Validate that tests pass and coverage meets requirements
   - Confirm the implementation follows the technical plan
